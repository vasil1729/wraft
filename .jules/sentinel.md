## 2024-06-25 - Prevent Timing and Enumeration Vulnerabilities in Elixir Auth Flows
**Vulnerability:** Elixir authentication endpoints (`SessionController` and `UserController`) were vulnerable to user enumeration via timing attacks and differential error messages. Specifically, `SessionController` evaluated user status (`is_deactivated`) and skipped `Bcrypt.verify_pass/2` for non-existent users, leaking if an email exists by returning faster. Furthermore, `UserController` leaked specific `{:error, :invalid_email}` messages that were translated by `FallbackController` to reveal if a user was in the system.
**Learning:** In Elixir `with` statements, placing business logic checks or implicit skips of password hashing before verifying the password hash can cause timing disparities. Also, controllers delegating to `FallbackController` must ensure they don't pass distinct error tuples that reveal internal state (like `invalid_email` vs `invalid_password`).
**Prevention:** Always extract user lookup into a standalone `case` statement. If a user does not exist, explicitly call `Bcrypt.no_user_verify()` to simulate the delay of hashing, and map the error to a generic tuple like `{:error, :invalid}`. Pass this result into the `with` statement, where `Bcrypt.verify_pass/2` and other status checks must be evaluated on the happy path. This keeps the timing consistent and hides enumeration details.
