## 2024-06-27 - [Fix User Enumeration and Timing Attack in Elixir Auth]
**Vulnerability:** User enumeration and timing attack in API sign-in flow (`UserController.signin/2`). If an invalid email was provided, `Account.find/1` would immediately return `{:error, :invalid_email}` and skip the password verification step. This bypassed the slow `Bcrypt` hashing algorithm, creating a noticeable timing difference that attackers could use to determine if an email exists. Additionally, the specific error `{:error, :invalid_email}` was caught by the `FallbackController` and returned as "No user with this email.!", leading to explicit user enumeration.
**Learning:** In Elixir authentication flows, utilizing `with` statements can inadvertently cause timing leaks if a failed user lookup short-circuits the password evaluation block. To mitigate this, `Bcrypt.no_user_verify()` must be explicitly called on paths where no valid user is found (e.g., `nil` or `{:error, :invalid_email}`) to simulate the password hashing delay. Furthermore, explicit errors like `{:error, :invalid_email}` must be sanitized and remapped to generic errors like `{:error, :invalid}` before being processed by the fallback controller. This prevents both timing-based and response-based enumeration vulnerabilities.
**Prevention:**
1. Always map specific lookup errors (e.g., `{:error, :invalid_email}`) to generic failures (e.g., `{:error, :invalid}`) in authentication endpoints.
2. Ensure the slow operation (`Bcrypt.verify_pass()`) or its equivalent simulation (`Bcrypt.no_user_verify()`) runs exactly once per authentication attempt, regardless of whether the user exists.
3. Handle user lookups explicitly with a `case` statement, strictly separating the execution paths to inject `Bcrypt.no_user_verify()` on failure without double-evaluating the password on success.
