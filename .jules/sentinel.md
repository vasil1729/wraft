## 2025-02-23 - [Elixir Authentication Timing Attack & Status Enumeration]
**Vulnerability:** The `SessionController.create/2` action used a `with` statement that first checked `is_deactivated: false` during user lookup, and only then verified the password. This allowed an attacker to enumerate account status (deactivated vs non-existent) based on the error messages or timing. Furthermore, it lacked a call to `Bcrypt.no_user_verify()` when the user was not found, opening the door to timing attacks that could allow enumeration of valid vs invalid email addresses.
**Learning:** Using `with` for user authentication logic can inadvertently leak state if status checks (like `is_deactivated`) are placed before password verification. The timing difference between an immediate failure and a Bcrypt hash verification allows attackers to determine if an email exists.
**Prevention:** Always restructure authentication logic to perform the user lookup unconditionally (e.g. `InternalUsers.get_by_email/1`). Then, use a `case` statement. If a user is found, always run `Bcrypt.verify_pass/2` first, before evaluating business logic flags (like `is_deactivated`). If the user is not found, always execute `Bcrypt.no_user_verify()` to simulate the timing of a password check and return a generic error message.
