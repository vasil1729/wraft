## 2025-03-01 - User Enumeration, Timing Attacks, and DoS Vectors in Elixir Auth Flows
**Vulnerability:** The authentication and password reset flows exposed whether user emails existed in the system. The login (`signin`) flow allowed enumeration via error messages or timing differences (e.g., exiting a `with` statement early before the password verification step). Meanwhile, adding `Bcrypt.no_user_verify()` to the unhappy path of the password reset (`generate_token`) flow could introduce a severe CPU-exhaustion Denial of Service (DoS) vulnerability, because the happy path does not verify a password.
**Learning:** In Elixir, mitigating timing attacks by unconditionally calling `Bcrypt.no_user_verify()` on failure paths can be dangerous. It must be carefully placed so that it simulates the timing delay *only* where an actual password hash would normally happen (like login). In flows where passwords aren't checked (like generating a reset token), we should simply swallow the error and return a generic success message without hashing. Additionally, extracting the user lookup into a `case` statement (rather than a `with` statement) helps control the timing execution flow and prevents implicit early exits from skipping the timing delay.
**Prevention:**
1. Always evaluate the happy path of a flow. If it doesn't hash a password, don't use `Bcrypt.no_user_verify()` on the unhappy path (DoS risk).
2. For login flows, explicitly handle `nil` or `{:error, ...}` user lookup results with a `case` statement that strictly calls `Bcrypt.no_user_verify()` and returns a generic `{:error, :invalid}`.
3. Return generic responses (e.g., `200 Success` or `{:error, :invalid}`) for both successful and failed user lookups in sensitive endpoints to prevent enumeration.
