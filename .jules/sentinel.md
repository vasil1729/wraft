## 2023-11-20 - Prevent Timing Attacks in Authentication Flows
**Vulnerability:** Timing attacks and user enumeration. If user lookup failed, the system skipped the slow `Bcrypt.verify_pass` operation, exposing whether an email or username existed by responding faster to invalid emails. Furthermore, checking business logic status flags (like `is_deactivated`) *before* password verification leaks account statuses.
**Learning:** In Elixir/Phoenix, short-circuiting `with` statements upon failed user lookups can cause timing leaks. `Bcrypt.no_user_verify()` must be explicitly called on the failure path to simulate password hashing delays. Additionally, placing status checks before password verification (e.g., early exits in a `with` statement) introduces a timing attack vector.
**Prevention:** Always separate the user lookup from password verification using a `case` statement. If lookup fails, immediately call `Bcrypt.no_user_verify()` and return a generic error. In `with` statements, ensure `Bcrypt.verify_pass` runs *before* checking business flags like `is_deactivated`. Also, explicitly map internal lookup errors like `{:error, :invalid_email}` to generic errors like `{:error, :invalid}`.
