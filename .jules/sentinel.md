## 2024-06-28 - [Timing Attack & User Enumeration in Elixir Authentication Flows]
**Vulnerability:** Elixir authentication flows can be vulnerable to timing attacks and user enumeration if the password verification function `Bcrypt.verify_pass/2` is not matched by a delayed action on invalid user lookups. Also, placing status checks (e.g., `is_deactivated`) before password verification introduces a timing attack vector. Missing a catch-all in `else` blocks can cause application crashes.
**Learning:** Short-circuiting `with` statements upon failed user lookups can cause timing leaks. Instead of placing `Bcrypt.no_user_verify()` unconditionally in the `else` block of a `with` statement that also evaluates the password (which may lead to double-hashing vulnerabilities), it's best to extract the user lookup, conditionally inject `Bcrypt.no_user_verify()` on failure, and pass the result into the original `with` statement.
**Prevention:** Always verify the user's password (`Bcrypt.verify_pass/2`) before checking business logic status flags like `is_deactivated`. When handling user lookups like `Account.find/1` in authentication flows, use a defensive `case` statement that explicitly matches the expected struct to trigger `Bcrypt.no_user_verify()` on failure. Map specific lookup errors (like `{:error, :invalid_email}`) to generic errors (like `{:error, :invalid}`) before returning them or passing them to a fallback controller to prevent user enumeration. Ensure a catch-all clause (e.g., `_ ->` or `error ->`) remains present in the `else` block of `with` or `case` statements.
