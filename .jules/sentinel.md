## 2024-05-18 - [Preventing Timing Attacks and User Enumeration in Elixir Auth]
**Vulnerability:** The application was vulnerable to user enumeration via timing attacks in the `signin` flow. `Account.find` failures (where an email doesn't exist) would return early, taking significantly less time than successful lookups where `Bcrypt.verify_pass` was evaluated. Further, the password reset endpoint returned distinct errors if the user didn't exist.
**Learning:** In Elixir `with` statements used for authentication, short-circuiting on failed user lookups can cause timing leaks. For login paths, we must explicitly call `Bcrypt.no_user_verify()` on these failure paths to simulate password hashing delays. For password resets, returning a generic success response regardless of user existence prevents enumeration without introducing Denial of Service (DoS) risks (avoiding `Bcrypt.no_user_verify()` on unhappy reset paths).
**Prevention:** To prevent double-hash timing attacks in Elixir authentication flows, use a `case` statement on the fetched user object to completely separate the execution path of `Bcrypt.verify_pass/2` (for existing users) and `Bcrypt.no_user_verify/0` (for non-existent users), rather than placing `Bcrypt.no_user_verify/0` unconditionally in the `else` block of a `with` statement that also evaluates the password. Always return generic responses for auth endpoints.
