## 2025-01-20 - Prevent double-hash timing attack in authentication flow
**Vulnerability:** A timing attack and user enumeration vulnerability existed in the `signin` authentication flow. When evaluating user existence with `with %User{} = user <- Account.find(email)`, early exits upon lookup failure lacked a simulated password hash (`Bcrypt.no_user_verify()`), allowing attackers to infer user existence based on response time. Additionally, `Account.find/1` returns `{:error, :invalid_email}`, which leaked that the specific email did not exist rather than throwing a generic error, due to the way `FallbackController` maps `{:error, :invalid_email}`.
**Learning:** It's important to simulate the expensive password hashing process even when a user is not found to prevent timing attacks. Because `with` statements short-circuit on non-matches, placing `Bcrypt.no_user_verify()` inside an `else` block alongside a password check is often complex and error-prone (as seen with "double-hash timing attacks"). Extracting the user lookup into a defensive `case` statement before the `with` block provides complete separation of the execution paths for existing and non-existing users. Furthermore, specific error returns like `{:error, :invalid_email}` should be re-mapped to generic errors like `{:error, :invalid}` for the `FallbackController` to avoid user enumeration.
**Prevention:** Always extract user lookups in authentication flows into a `case` statement, implementing a wildcard catch-all (`_ ->`) that explicitly triggers `Bcrypt.no_user_verify()` and maps errors to `{:error, :invalid}` before passing the result to the main `with` block. Use `Map.get(params, "key")` instead of pattern matching for optional inputs to avoid bypasses on missing keys.
