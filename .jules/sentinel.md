## 2024-07-11 - Timing attack and account enumeration in SessionController
**Vulnerability:** The `SessionController.create/2` action used a `with` statement that first checked if the user existed and was active (`%InternalUser{is_deactivated: false}`). If the user didn't exist, it skipped the password hashing completely and immediately returned an error. If the user existed but was deactivated, it returned a specific error message.
**Learning:** This allowed attackers to enumerate whether an email exists in the system via timing attack (fast response = user doesn't exist, slow response = user exists). It also allowed enumerating account statuses. Short-circuiting `with` statements without mitigating hashing delay when user lookup fails creates timing attacks.
**Prevention:** Use a `case` statement for user lookups. Separate the password verification and status checks. For non-existent users (e.g., matching `_ ->`), explicitly call `Bcrypt.no_user_verify()` to simulate hashing delay and return generic error messages. For existing users, verify the password *before* checking business logic like `is_deactivated` to avoid status enumeration.
