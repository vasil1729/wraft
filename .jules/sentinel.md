## 2025-02-24 - [Fix Authentication Timing Attacks and User Enumeration]
**Vulnerability:** The application was vulnerable to user enumeration via timing attacks and differential responses. In `SessionController` and `UserController`, early returns in `with` statements skipped computationally expensive `Bcrypt.verify_pass/2` calls when an email was not found, or checked status flags (`is_deactivated`) before verifying passwords. Additionally, the password reset endpoint returned distinct errors (`{:error, :invalid_email}`) instead of a generic success message, allowing an attacker to enumerate valid email addresses.
**Learning:** In Elixir/Phoenix authentication flows using Bcrypt, using `with` statements to handle user lookups can introduce timing leaks. If a user is `nil`, the `with` statement short-circuits, resulting in a much faster response time compared to a valid user whose password hash must be verified. Also, checking business logic flags (like active status) before verifying credentials provides another timing side-channel. Finally, password reset flows must always return a generic success message to prevent simple enumeration.
**Prevention:**
1. Always use nested `if/else` or explicit `case` blocks instead of `with` for authentication flows to guarantee that `Bcrypt.verify_pass/2` is called exactly once.
2. If a user lookup fails (i.e., `user` is nil), explicitly call `Bcrypt.no_user_verify()` to simulate the delay of password hashing.
3. Always verify the password *before* checking account status flags like `is_deactivated`.
4. Ensure password reset/forgot password endpoints return a generic `200 OK` ("Success") response regardless of whether the email exists in the system. Do NOT use `Bcrypt.no_user_verify()` on the unhappy path of a password reset flow, as this can introduce a DoS vulnerability.
