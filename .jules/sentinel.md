## 2024-05-17 - Prevent User Enumeration and Timing Attacks
**Vulnerability:** The authentication flows (`WraftDocWeb.SessionController.create/2`, `WraftDocWeb.Api.V1.UserController.signin/2`, and `generate_token/2`) leaked the existence of user emails. In the login endpoints, timing attacks were possible because the slow bcrypt password hashing was only performed if the user existed. Furthermore, `generate_token/2` returned an error for invalid emails, making user enumeration trivial. Finally, status flags (`is_deactivated`) were checked before password verification, allowing attackers to enumerate account statuses via timing analysis.
**Learning:** Short-circuiting execution flows (like Ecto `case` or `with` blocks) upon failed user lookups skips the computationally expensive `Bcrypt.verify_pass/2`, leading to observable timing differences. Additionally, providing different HTTP responses for valid vs invalid emails during password resets exposes the user base.
**Prevention:** To prevent user enumeration via timing attacks, ensure the slow operation is simulated by invoking `Bcrypt.no_user_verify()` exactly once when a user lookup fails. However, for password reset flows, do not call `Bcrypt.no_user_verify()` to avoid CPU exhaustion Denial of Service (DoS) attacks; simply return generic success responses. Status flags (`is_deactivated`) must only be verified after a successful password check.
