## 2024-05-18 - [Fix Timing Attack and User Enumeration in signin]
**Vulnerability:** The `signin` function was vulnerable to a timing attack and user enumeration. Specifically, `Account.find/1` could return `{:error, :invalid_email}` which implicitly allowed distinguishing between valid and invalid emails by breaking the `with` block and skipping the computationally expensive `Bcrypt.verify_pass`. This created a time discrepancy. Additionally, mapping `{:error, :invalid_email}` directly through the `FallbackController` leaked information about whether the email existed. Lastly, passing an empty password would bypass Bcrypt completely on invalid accounts.
**Learning:** In Elixir `with` statements, early failures (like missing users) skip subsequent checks (like `Bcrypt.verify_pass`). This creates significant timing differences between existent and non-existent users. We must extract the user lookup into a `case` statement, call a dummy computationally equivalent function (`Bcrypt.no_user_verify()`) when the user is not found, and map any lookup errors explicitly to a generic response tuple like `{:error, :invalid}`.
**Prevention:** Always separate user lookup from password hashing. In the failure path of the user lookup, ensure you execute `Bcrypt.no_user_verify()`. Check for empty/nil passwords before running the lookup or hashing steps. Always return generic error tuples (e.g., `{:error, :invalid}`) for authentication failures rather than bubbling up specific errors (e.g., `{:error, :invalid_email}`) which can be exposed by the FallbackController.
