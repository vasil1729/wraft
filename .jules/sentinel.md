## 2024-05-19 - [Fix Timing Attacks in Signin Flows]
**Vulnerability:** User enumeration timing attacks existed in `UserController.signin/2` and `SessionController.create/2`. In both locations, an early return or branch occurred if the user didn't exist or was deactivated, meaning `Bcrypt.verify_pass/2` was skipped.
**Learning:** Returning early or placing `Bcrypt.no_user_verify/0` conditionally inside `else` blocks of `with` statements can lead to double-hash timing leaks or bypass normal FallbackController mapping. Admin authentication using `cond` or `with` statements that branch on flags like `is_deactivated` before hashing passwords also create noticeable timing differences.
**Prevention:** Extract user lookups into a defensive `case` or generic variable lookup. Use conditional checking to invoke `Bcrypt.no_user_verify()` for unknown users. Deactivated status checks must only be resolved *after* `Bcrypt.verify_pass/2` executes. Map specific errors (e.g., `{:error, :invalid_email}`) directly to `{:error, :invalid}` for standard generic message mitigations.
