## 2024-05-24 - [User Enumeration via Timing Attacks in Authentication]
**Vulnerability:** User enumeration vulnerability existed in `SessionController` and `UserController` because user existence was checked before verifying the password, and if the user didn't exist or was deactivated, the password check was skipped entirely. This created a measurable timing difference between valid and invalid email addresses. Additionally, `UserController` leaked specific errors (`{:error, :invalid_email}`) which resulted in distinct messages based on account existence.
**Learning:** In Elixir/Phoenix, early exits in `with` statements during authentication flows (like `Account.find` returning an error, or checking `is_deactivated` before `verify_pass`) cause computation-heavy bcrypt operations to be skipped. This leads to severe timing differences that allow attackers to enumerate user accounts. Returning specific errors instead of generic ones compounds this issue.
**Prevention:** Always ensure computationally expensive operations like `Bcrypt.verify_pass/2` are executed exactly once. When user lookup fails, explicitly call `Bcrypt.no_user_verify()` to simulate the delay. Always return a generic error message (e.g. `{:error, :invalid}`) for both incorrect emails and incorrect passwords. Avoid checking business logic flags (like `is_deactivated`) before verifying the password.
