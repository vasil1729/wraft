## 2026-06-14 - Prevent Authentication Enumeration and Timing Attacks
**Vulnerability:** User enumeration risks existed in the authentication flows (`UserController.signin` and `SessionController.create`) due to missing artificial hashing delays when an email lookup fails, allowing attackers to distinguish between existing and non-existing users based on response times. Additionally, `SessionController` evaluated `is_deactivated` before hashing passwords, allowing status enumeration without credentials. The `FallbackController` also exposed specific error messages (`{:error, :invalid_email}`). Finally, the password reset token endpoint (`UserController.generate_token`) lacked generic responses on failure, which if fixed by unconditionally applying `Bcrypt.no_user_verify()` would have introduced a CPU-exhaustion DoS attack surface.
**Learning:** In Elixir, `with` statements can inadvertently leak timing information or exact error types if unhappy paths are not meticulously handled. When an entity is not found, a defensive `case` block must explicitly invoke `Bcrypt.no_user_verify()` to simulate hashing delays, while error returns must be generalized to avoid leaking existence via fallback handlers. However, applying this artificial delay to password reset endpoints introduces a severe DoS vulnerability because the happy path does not verify passwords.
**Prevention:** Always verify passwords before checking account status flags. Implement safe lookups that inject `Bcrypt.no_user_verify()` and standardize error responses (e.g., `{:error, :invalid}`) for login endpoints. For token generation/reset endpoints, return an unconditional success response without inducing artificial hashing delays.
