## 2024-06-09 - [Fix timing attack in SessionController]
**Vulnerability:** The session controller (`SessionController.create/2`) evaluated a user's deactivated status before checking their password (`with %InternalUser{is_deactivated: false} = user <- ...`). This allowed for a timing attack because short-circuiting out of the `with` block would skip hashing. An attacker could enumerate active vs deactivated accounts and valid vs invalid emails because missing users didn't trigger a hashing delay either.
**Learning:** In authentication flows (especially Elixir `with` statements), always verify the password (`Bcrypt.verify_pass`) *before* checking business logic flags like `is_deactivated` or other status flags. This ensures the slow hashing step runs consistently for all existing users. If the user lookup fails, we must explicitly call `Bcrypt.no_user_verify()` to simulate the delay.
**Prevention:** Avoid putting business logic validation (like `is_deactivated: false`) inside the user lookup match within authentication `with` blocks. Always perform a generic lookup, verify the password, and handle status errors *afterward*. And always ensure missing accounts get a `Bcrypt.no_user_verify()` call.
