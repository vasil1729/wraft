## 2024-06-06 - [Timing Attack and User Enumeration in Auth Flows]
**Vulnerability:** The authentication flows (`signin/2` and `generate_token/2`) leaked user existence. The `signin` endpoint did not perform slow password hashing if the user email wasn't found, leading to a timing attack where an attacker could deduce valid emails by response time differences. The `generate_token` endpoint returned different outcomes depending on if the user existed or not.
**Learning:** In Elixir authentication flows, short-circuiting statements (like `with`) upon failed user lookups can cause timing leaks. Generic errors must be returned along with performing an explicit dummy slow operation (`Bcrypt.no_user_verify()`). For password reset flows (`generate_token`), always return generic success messages to avoid user enumeration without executing dummy hashing to avoid a CPU-exhaustion Denial of Service (DoS) vulnerability.
**Prevention:** Always call `Bcrypt.no_user_verify()` explicitly in the controller on unhappy authentication paths. Map specific lookup errors to generic errors (e.g., `{:error, :invalid}`) before returning them or passing them to `FallbackController`. For token generation, ensure all paths (success and failure) yield the same successful response without unnecessary operations.
