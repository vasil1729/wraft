## 2024-05-24 - [Fix user enumeration and timing attack in API user login flow]
**Vulnerability:** The API login endpoint (`WraftDocWeb.Api.V1.UserController.signin/2`) leaked whether an email address exists through both timing differences (Bcrypt was only called if a user existed) and explicit error responses (`{:error, :invalid_email}` mapping to a specific FallbackController message). Additionally, the password reset endpoint (`generate_token/2`) used a `with` statement that implicitly fell back to an error (exposing enumeration) instead of always returning a success response.
**Learning:** `with` statements can unintentionally create vulnerabilities in security flows by exposing error states that differ between success and failure paths. Specifically, early short-circuiting on failed user lookups skips expensive operations (like password hashing), enabling timing-based enumeration.
**Prevention:** Always ensure expensive operations (like `Bcrypt.verify_pass/2` or `Bcrypt.no_user_verify/0`) take comparable amounts of time regardless of whether a user exists. Explicitly map granular errors (like `{:error, :invalid_email}`) to generic responses (`{:error, :invalid}`) before they reach the fallback controller. For password resets, always return a generic success message regardless of the backend operation's success to prevent enumeration. Do not use `Bcrypt.no_user_verify/0` on password reset flows, as it introduces DoS vulnerabilities since no password verification happens on the happy path.
