## 2024-07-01 - User Enumeration and Timing Attacks in Authentication Flows
**Vulnerability:** The application was vulnerable to user enumeration and timing attacks during login and password reset flows. Specifically, `WraftDocWeb.Api.V1.UserController.signin/2` short-circuited when `Account.find/1` failed, causing a timing discrepancy due to missing bcrypt hashing, and leaking `{:error, :invalid_email}` messages. `generate_token/2` would not return generic responses for non-existent users, leaking valid emails.
**Learning:** In Elixir `with` statements used for authentication, short-circuiting on failed user lookups bypasses password verification, introducing timing attacks. Simply putting `Bcrypt.no_user_verify()` in an `else` block can be problematic if password verification is also in the `with` statement, as it can lead to double-hashing or incorrect error masking. Password reset flows should avoid `Bcrypt.no_user_verify()` entirely to prevent CPU-exhaustion Denial of Service (DoS) since the happy path doesn't do a heavy computation.
**Prevention:**
1. For login flows, explicitly handle user lookup failure before evaluating the password. If lookup fails, simulate password hashing with `Bcrypt.no_user_verify()` and map the specific error to a generic `{:error, :invalid}`.
2. For password reset and generic endpoints that do not check passwords on the happy path, never use `Bcrypt.no_user_verify()` on the unhappy path to avoid DoS. Always return a generic success message regardless of whether the user exists or not.
